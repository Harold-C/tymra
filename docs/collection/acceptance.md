# 本地数据采集验收标准

Last updated: 2026-08-06

**状态：** 所有在本地开发环境实现的数据采集渠道都必须遵守的项目标准。

本地验收用于证明真实传输、解析、持久化、幂等和安全控制在一个有边界的开发运行中可用。它不等同于生产启用、全国完整性、生产容量或多日无人值守稳定性验收。基础控制证据保存在[2026-07-21 本地采集验收快照](../evidence/collection-acceptance-2026-07-21.md)，统一 17 来源两轮真实运行保存在[2026-07-30 公开来源验收](../evidence/public-source-acceptance-2026-07-30.md)。两者都是历史快照，不自动代表当前外部来源可用。

## 环境边界

- `localAcceptance` 只允许在 `NODE_ENV=development` 下运行。
- Scheduler 必须关闭；验收不得创建、启用或修改计划任务。
- 数据源需在开发环境启用，但本地验收不要求或写入 `approved-by`、`license-basis`，也不得改变审批、权利、生命周期、健康或运行状态。
- 生产启用是独立的运维决策，不由本地验收自动触发。最新统一 34 来源、68 pass 结果见
  [2026-08-06 operational hardening acceptance](../evidence/operational-hardening-acceptance-2026-08-06.md)。

## 有边界的真实采集

- 使用真实公开来源及生产预期的只读传输和解析器，不用 fixture 代替真实来源。
- 在请求前由代码固定页数、记录数、请求预算、并发、延迟、超时和响应大小上限。
- 不登录、不提交表单、不绕过挑战、不购买、不执行任何远端写操作。遇到验证、限流或挑战时停止批次并记录分类。
- 使用每个来源的分布式锁，重叠任务必须安全失败。
- 每次运行持久化不可变的 `CollectionRun`，记录 `localAcceptance=true`、有效边界、计数器、结果和失败分类。

## 持久化与证据

- 保存短期原始证据或证据指针，包括哈希、来源/运行链路、敏感数据分类和明确过期时间。
- 成功证据使用普通短 TTL；解析失败、失败捕获和人工处理状态使用较长失败 TTL。
- 先保存来源标准化记录，再保存 canonical 记录，并保留明确的来源映射、匹配方式和置信度。
- 发现进度必须持久化；不完整发现不能停用未出现的目标。
- Job 使用持久租约，只能在租约过期后由其他 Worker 回收。

## 两次真实运行

同一有边界的真实采集必须连续运行两次：第一次证明发现、解析、标准化、持久化和链路；第二次证明稳定标识的幂等 upsert。

验收至少记录：运行 ID 与范围、请求/页面/发现/详情/成功/失败数、两次运行后的来源与 canonical 行数、第二次新增与更新行数、证据和 TTL、运行前后治理状态、计划任务状态和运行时健康。

## 自动化门槛

每个渠道必须覆盖：

1. 解析成功、来源变体及缺失字段的保守处理；
2. 持久化、来源到 canonical 的链路和两次运行幂等性；
3. 成功/失败证据的 TTL 选择及时间推进清理；
4. 部分发现安全，以及适用时的限流/挑战停止逻辑；
5. `test`、`production` 和 Scheduler 开启时拒绝本地验收；
6. Redis 来源锁的竞争、释放和重获；
7. Job 租约过期后才能回收；
8. 来源治理和计划任务保持不变；
9. 完整 `pnpm verify`：lint、typecheck、unit、integration 和 production build。

只有上述适用门槛都有实际证据时才使用 `locally verified`。未适用项必须明确说明，不能把本地成功扩大成生产或长期稳定性结论。
