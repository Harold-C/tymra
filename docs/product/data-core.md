# Tymra 新西兰全国住宿数据核心契约

状态：Active — National Data Core Baseline v1.0
Owner / 最终批准人：Harold
内容基线更新：2026-09-28；访问阶段说明校准：2026-10-06

本文件是 Tymra 当前全国数据核心的执行契约。它定义当前要建设和持续运行的数据资产、覆盖层、来源能力、时间语义、质量、历史、证据与 lineage。客户会员产品与后台进入同一生产部署；权益由 `membership-plans.md` 定义，初期只隐藏首页、公共导航和营销 CTA 入口。

以下定义已批准的完整目标；实际 Admin-only 生产阶段与未完成验收见[产品入口](README.md#approved-target-and-operational-stage)及[追踪表](../traceability.md)。

## 1. 当前部署与展示

- 同一生产版本部署采集后台、Worker、调度、来源健康、异常处理、全国覆盖、公开 Price Check、客户注册／登录、四档会员、方案价格、Stripe、客户结果和监测。
- 初期状态为 `DEPLOYED_HIDDEN`：首页、公共导航和营销 CTA 不展示客户入口，但路由、API、Worker、数据库和 webhook 随版本部署并接受生产验收。
- 隐藏入口不是安全措施。直接访问继续执行身份认证、资源归属、方案权益、防滥用和支付状态检查。
- 在完整客户端已通过生产门槛且直接路由已开放的 `DEPLOYED_HIDDEN` 阶段，恢复发现入口只改变展示配置并完成回归。由 Admin-only 进入该阶段还须通过客户端门槛及明确的 ingress/access-mode 变更，不建立另一套客户端部署。

## 2. 全国覆盖的五层定义

### DATA-CORE-001 全国身份目录

持续建立全新西兰 Property、Sellable Unit、Listing、标准地址和地理层级的稳定身份目录。目录覆盖目标是全国，不以 Christchurch 或少数主要城市代替全国。

Airbnb／Bookabach 公开预览未披露精确地址时，已核实的来源房源 ID、同房源大概位置与
公开物理容量可以建立 `SOURCE_SCOPED` 身份并继续读取该来源报价。精确地址／坐标
保留未知，大概地图点单独保留精度；不据此跨平台合并或计入已确认唯一物理物业／Unit
覆盖。已有可靠精确映射仍沿用，不以大概位置覆盖。代表性全国覆盖与生产报价门槛另行验收。

### DATA-CORE-002 全国公共市场信号

持续采集与住宿需求、供给、交通可达性和异常相关的全国公共信号，包括节假日、学校假期、大学关键日期、活动、港口／邮轮、机场、道路、天气、自然事件和适用的宏观数据。信号必须绑定明确区域、时间、来源、Freshness 和 Confidence。

### DATA-CORE-003 代表性 OTA 面板

按 Region、Territorial Authority、住宿类型、质量档位和价格档位维护分层 OTA 样本，持续观察公开价格、可售、限制和 Listing 变化。代表性面板不承诺抓取所有房源未来 365 天的所有 OTA 组合。

### DATA-CORE-003A 城区分层、代表性选样与量化标签

2026-10-14 确认以 **城区（Locality）→ 城市／Territorial Authority → 大区（Region）** 组织样本。
基础选样格为「城区 × 住宿类型」，地理归属必须有坐标／已核实地址、稳定 ID、边界版本和证据；
不从房源名称猜城区，不强行套用可能跨界的地名层级。向上汇总沿用核实的地理归属。
初版 40 个仅为历史容量示例。2026-10-14 后续确认取消固定数量，以实际地理／类型覆盖、
资料可用性和持续经营证据决定主样本数量；数量变动须重新计算预算，不能自动扩大运行额度。

先核实各格的去重合格供给，再审核分配目标，兼顾核心和外围城区及真实存在的住宿类型。
类型词表覆盖酒店、汽车旅馆、服务式公寓、整套度假屋、客栈、旅舍、背包客住宿、假日公园、农场住宿等；
单晚与两晚试点分别固定两成人／一单元及真实晚数；两晚以实际套餐总额为主，不能将单晚乘二、清洁费按晚翻倍或混算两组。
来源内观察、可比报价和正式区域面板分别准入，具体门槛见下方分阶段规则；其他晚数保留为范围缺口。
同格内优先补足不同价位、容量和物理单元类型，并增加空间分布；评分高低和 OTA 排名不作为优先入选依据。
同一物业跨平台只计一次，身份冲突阻止入选；稀缺格缺额不能偷偷借用其他城区或类型补足。
该规则产生可审核的目的性分层选样建议，不证明概率抽样代表性，不提供虚构的误差范围。

每个候选和冻结样本使用版本化标签 `market-sample-labels-v1`，测量值均保留来源、观察时间、方法版本和单位：

| 标签组 | 字段与分析口径 |
| --- | --- |
| 地理 | Region／Authority／Locality ID、经纬度、边界版本及归属方法 |
| 类型与规模 | 住宿类别；整套／独立房间／共享房间／床位／营位；可住人数、卧室数、床数、面积 m² |
| 设施 | 厨房、停车位、独立卫浴，布尔值；未知不等于没有 |
| 品质与口碑 | 有来源的官方星级；各平台原始评分、满分尺度、评论数；100 分换算仅换尺度，不跨平台平均或视为正确率 |
| 价格 | 同条件基线中位价（NZD 分）、报价数、观察日数、窗口、查询／条款／采集环境；价位档及参考组、阈值版本 |
| 采集质量 | 窗口内请求数、可比成功数、失败数及可比成功比例；零请求时比例未知 |

未知值保留 null／UNKNOWN，不填零、不从两成人查询推定实际容量、不从星级推定价格档。
价格档必须有同条件基线及明确参考组；参考组应保持城市、类型、单元和报价条件一致，未知档不算已覆盖价位。
冻结前必须审核身份、三级地理、住宿／单元类型、至少两成人容量、精确房型及条款／环境；
面积、设施、星级等可缺失但必须披露，不能为了标签齐全编值。冻结后更新标签或更换样本需保留旧版本及审核原因。

城区、城市及大区的价格水平与变化指数分开定义；不同物理单元、住宿类型和报价条件先分开比较。
向上汇总不得直接平均城区中位数、按抓取条数加权，或把已采到的几个城区称为整个城市。
供给数、来源和日期齐备时可计算格内供给／样本数的扩展因子，但目的性选样的该因子并非已知入选概率的倒数。
正式指数还须审核完整供给框、缺失格、固定权重与匹配样本覆盖；供给未知时只展示已观察样本范围。
本次只实现本地标签合同、选样建议和计划检查，向上汇总指数及真实采集接线仍须另行完成验收。

固定物业名单与可执行报价面板分别管理。优先固定地址、持续住宿经营、多单元或明确长期经营模式；
保留经营年份证据、全年营业自述、未来日期库存核验数、历史观察跨度和房型变更记录。
官网存在／历史建筑年龄／品牌经营年限均不等于该物业持续营业证明，不给未经校准的存续概率。
单套度假屋、季节或特色住宿单独观察，不能因担心流失而隐瞒该市场的覆盖不足。
正式多窗口基线前核对未来 30／90／180 天工作日／周末窗口与最低晚数；小范围观察可先锁定两个未来入住日，不要求六窗都有库存。库存不足、售罄、来源故障、
暂停销售及确认退出分别记录。候补不进入分母，不自动替换；确认退出保留历史及流失分母，
新物业须同区同类审核和重叠观察后在新版本加入，防止幸存者偏差。

候补按主样本逐个映射，区分专属第一候补、共用候选池与同格缺口；同一物业最多接替一个席位，
不能把主样本互相充作候补。城区与住宿类型相同只是候选门槛，正式替换还须核对单元形态、容量、
设施、可比价位、条款和采集环境；无法匹配时保留缺口或新建独立批次，不跨区补足分母。
候补维护与替换重叠观察纳入显式预算。暂时无价格不触发自动换样，重试不重复计为多个观察日。

2026-10-15 确认分阶段准入，取代将所有正式面板/候补要求前置到观察入口的做法：

- **来源内观察**：有证据的来源房源ID、可重复识别的单元（来源房型ID、已审核唯一房型描述，或整套listing）、
  两成人查询支持及明确冲突记录。实际两成人选定报价仅证明查询支持，不得填写未知的最大容量。
  未公开精确地址可保留SOURCE_SCOPED，不跨平台强行合并或计入已核城区覆盖；房型描述需在执行前验证能够唯一选择。
- **报价可比**：按每条报价审核同一单元/入住日期/人数/晚数/币种/不可变匿名环境、完整必收费用及明确条款。
  未知费用、取消金额/文字冲突、身份或环境变化阻止该报价比较，原始观察保留；不因此永久排除房源。
  REQUEST_TO_BOOK单独比较申请报价，不能当作即时可订或与INSTANT混算。无库存、限制和技术失败不当成零价。
- **正式面板及区域发布**：继续执行已审核canonical身份、地理、容量/类型/单元标签、条款/环境合同；
  发布区域趋势另需供给框、固定权重、覆盖与代表性审核。观察名单不是冻结面板，也不通过页面的少量物业门槛替代区域验收。
- 24个月经营记录、长期不下线保证、多日稳定性、六个日期全部可订、每个对象已有独立候补，均不是第一次观察的前提。
  历史经营证据用于排序；持续性通过未来观察验证；候补缺口明示，同小区不同单元不能推定经营独立，主样本不互作候补。
- **执行授权独立**：观察准入、可比报价和本地计划都不启用采集；先核验来源能力/成本/额度及执行链路，再取得启动授权。
试点复核阈值、观察窗口与机器准备输入见 Argus 合同；Tymra 仍拥有业务判定和计划，Argus 执行浏览器任务。

### DATA-CORE-004 全国按需采集

#### 2026-10-18：Christchurch 样本报价走势

在既有68席正式采集之上提供只读的 `sample-quote-trends-v1`，不改变成员、调度、重试、
来源政策或原始记录，也不把 RAW_ONLY 改写为正式可比 RateObservation／城市指数。
它描述已观测样本的来源内显示报价，不是成交价、入住率或基督城供给加权指数。
来源执行器／Connector版本属于该参考口径的可见执行分组，不证明浏览器登录状态、
IP地区或个性化环境；该限制持续披露，不能制造 collectionProfile 或 bookingMode。

公开／合作方住宿总价须为同单元、明确入住退房日、2成人0儿童1套、NZD、实际一晚或两晚，
来源明确含必付费用，且餐食、取消、付款原文足够明确。来源套餐编号与已知条款组成精确签名；
来源未提供编号时，仅唯一明确的可见条款集合可作选择器，不制造OTA套餐编号；同条件有多个金额或身份歧义时排除。
未知／污染／冲突阻止该报价计算涨跌，但保留原始显示和缺口。公开价与合作方围栏不交叉匹配。
会员参考是独立的显示金额序列，须有同房源／单元、明确会员标签及会员套餐编号；
不借公开套餐的费用／条款，不宣称会员资格、可订库存或含完整费用，不并入公开总价。
一晚、两晚、住宿类型、来源、报价围栏及精确入住日期分别匹配；新房源不继承退出房源价格。

每个固定7日NZ采集周期，对同成员／入住窗口只取最后一次已完成运行，失败、无房和限制不补零、
不沿用本周期早期价格。重复验收不制造多个周次。涨跌只比较相邻周期同时出现的同一套餐，
每样本先汇总其匹配套餐变化，再对样本取中位变化；套餐多的物业不多占权重。
样本价格中位数仅为当期描述，不以不匹配的两期中位数相减。无配对或跨缺失周期时变化为空。

固定入住日序列显示观察日期和实际提前天数，提示包含临近入住的影响；换入住月份另开序列，
不把12月与1月连线。提前期筛选只限制观察范围，不把同一宽区间当作等价提前期，
不声称已剥离季节／活动／提前期影响。首个周期仅展示基线和等待下一周期，不能编造历史。
成员缺地理／住宿形态标签时不冒充已核城区覆盖。分析准入与采集准入分开；
字段不足不暂停正常采集，不自动补采、重试、恢复或替换。

内部运营者可以对任意可可靠解析的新西兰地址或受支持 OTA Listing URL 发起有界采集。地址模式返回附近公开住宿行情，Listing 模式返回目标 Listing 的公开价格；两者不得混淆身份或价格归属。

### DATA-CORE-005 会员激活房源监测

激活 Property 按会员方案执行逐日精确价格与长期监测。该层随同一生产版本部署；初期客户入口为 `DEPLOYED_HIDDEN`。

## 3. 区域覆盖与质量

### DATA-CORE-006 区域接受原则

所有新西兰 Region 都属于当前采集范围。区域不得因为不在 Christchurch 而被拒绝；无法解析身份或来源完全不可用时按具体失败原因停止。

### DATA-CORE-007 覆盖等级

每个区域和数据域分别返回 `SUPPORTED`、`PARTIAL_COVERAGE`、`PILOT`、`INSUFFICIENT_DATA` 或 `SOURCE_UNAVAILABLE`。覆盖等级必须由实际样本、成功率、Freshness 和质量决定，不由营销目标决定。

### DATA-CORE-008 覆盖事实

至少保存已知 Property／Unit／Listing 数、地理覆盖、样本构成、最近 24／72 小时覆盖率、采集成功率、来源失败率、最近成功时间、最近健康时间和覆盖缺口。全国总数必须能够下钻到 Region 和适用的 Territorial Authority。

## 4. Source Registry 与能力契约

### DATA-CORE-009 Source Registry

每个来源保存稳定 Source Key、提供者／站点身份、数据域、获取方式、生命周期、启用状态、健康状态、计划频率、并发／预算边界、负责人、保留策略、最后检查时间和最后成功时间。

### DATA-CORE-010 Capability-based adapter

来源只实现自身实际支持的能力，不要求所有来源伪造统一 OTA 方法。能力注册表至少允许：`discoverListings`、`resolveListing`、`collectRates`、`collectAvailability`、`collectEvents`、`collectKeyDates`、`collectTransportSignals`、`collectWeatherSignals`、`importDataset` 和 `healthCheck`。任务编排必须先检查 capability、启用状态和健康状态；缺少能力时 fail closed，不用空实现伪装成功。

当前 OTA 执行集合只包含 Booking.com、Airbnb、Expedia、Bookabach、Agoda 和 Trip.com。其他 OTA 不属于当前合同、发现、健康或验收范围，不保留兼容要求。

当前 Source Registry 和验收报告必须直接从实际启用配置生成，不使用历史来源数量作为当前基线。

## 5. 数据分层与证据保留

### DATA-CORE-011 三层数据

- Raw evidence：HTML、截图、响应片段或导入原件，用于解析、复核和故障诊断。
- Normalised fact：身份、价格、可售、事件、日期和市场信号的结构化观察。
- Derived result：快照、覆盖指标、异常、趋势、Confidence、推荐和其他分析结果。

三层拥有独立保留与清理策略，不能用客户历史权益延长原始证据保留，也不能因 Argus 清理短期证据而删除已确认的标准化历史。

### DATA-CORE-012 Argus 与 Tymra 边界

Argus 在 Tymra 校验结果和证据哈希并正确 ACK 后，可以按合同立即 purge Job 结果、HTML 和截图。Tymra 只保存业务必需的标准化事实、来源和 Job 标识、字节数／内容哈希、采集上下文、质量状态、解析器版本及转换链。需要延长诊断证据时必须在 ACK 前按批准的隔离流程保留，不得默认复制 Cookie、Session、Token 或浏览器 Profile。

## 6. 时间、Freshness 与 Confidence

### DATA-CORE-013 时间字段

每条事实按适用性分别保存：

- `sourcePublishedAt` 或 `sourceEffectiveAt`：来源发布或事实生效时间；
- `collectedAt`：Tymra／Argus 实际观察时间；
- `businessDate`、`validFrom`、`validTo`：事实适用的新西兰日期或区间；
- `ingestedAt`：进入 Tymra 标准化存储的时间；
- `supersededAt`：被新版本替代的时间。

所有业务日期和额度边界使用 `Pacific/Auckland`；机器时间戳以 UTC 保存并显式转换。无 `collectedAt` 的观察不得进入正式分析；缺少业务适用时间的数据不得绑定日期级结论。

### DATA-CORE-014 Freshness

Freshness 是按数据域、预测跨度和使用目的计算的独立状态，至少包含策略版本、计算时间、年龄、允许上限和 `FRESH`／`AGING`／`STALE`／`UNKNOWN`。OTA 价格、事件状态、道路警报和月度宏观数据不得共用同一个 24／72 小时阈值。

### DATA-CORE-015 Confidence

Confidence 分为 identity、field／observation、snapshot 和 derived-result 四层，并记录规则版本和限制原因。来源数量、身份匹配、字段完整度、时间一致性、可比性和冲突分别贡献质量判断；Confidence 不得替代 Freshness，也不得仅因数据存在而自动提高。

### DATA-CORE-015A 当前与未来优先的采集时间语义

本文件覆盖的所有渠道按其事实类型选择适用时间：活动、校历、节假日、航班／邮轮、天气／道路警报及 OTA 入住价格与可售，优先采集当前仍有效及未来日期；已结束的事实留作历史，不因滚动窗口前移而删除。改期、取消、撤稿和字段变化须保留来源事实的先后版本及对应采集批次，当前视图只显示仍有效的版本，历史视图可查询过去和被替代的版本。

机场月报、汇率、旅游统计等按发布周期提供过去期间数据的渠道，以最新已发布或最新可取得的期间为增量目标，并保存其业务期间与采集时间；不得为了满足未来窗口而伪造未来数据。跨年来源要随新西兰业务日期滚动到新年度。自动补齐受来源自身的请求预算、访问限制和逐步放量门槛约束，不能以一次成功读取代替持续采集验收。

## 7. 身份、历史与 lineage

### DATA-CORE-016 版本化身份图谱

标准地址、Property、Sellable Unit 和 Listing 的关系使用带 `validFrom`／`validTo` 的版本记录，保存匹配依据、Confidence、首次发现、最后确认、冲突、合并和拆分。地址写法或 OTA 渠道变化不得把同一物理住宿重复计数。

### DATA-CORE-017 Listing 变化历史

Listing 的首次发现、下线、重新上线、名称、品牌、房型、政策、公开价格、可售和身份映射变化采用追加事件或版本记录；当前快照可以物化，但不得覆盖唯一历史事实。

### DATA-CORE-018 Data Lineage

每个标准化事实、MarketSnapshot、DateSnapshot、Insight 和 Result Version 必须能追溯至 Source、Collection Run／Argus Job、查询条件、标准化输入、转换／解析器版本、人工修改和保留的证据引用或哈希。转换链使用可重放的 `TransformationRun` 与输入／输出 lineage edge 表达；只保存最新外键不足以满足该要求。

## 8. 快照与结果语义

### DATA-CORE-019 快照目标类型

MarketSnapshot 必须区分 `LISTING_PRICING` 和 `LOCATION_BENCHMARK`。Listing 模式要求 `targetListingId`；地址模式要求稳定 `propertyId`／空间锚点且允许 `targetListingId=null`。Schema 不得为了复用 Listing 模式而给地址模式伪造目标 Listing。

### DATA-CORE-020 价格与推荐分离

价格事实和调价推荐是两个独立输出。任一模式只要取得至少一个可验证、可归属且查询条件一致的公开价格，就记录 `priceResultStatus=COMPLETED` 并返回全部有效观察；单来源、竞品不足或市场信号不足只影响 `priceEvidenceStatus`、`recommendationStatus` 和 Confidence。只有没有任何有效价格，或身份、日期、币种、入住条件、价格口径无法确认时，价格结果才可为 `PARTIAL`、`INSUFFICIENT_DATA` 或其他阻断状态。

## 9. 当前统一生产验收边界

### DATA-CORE-021 全国数据后台门槛

当前阶段完成定义至少包括：全国调度可配置且默认安全；来源 capability、健康、熔断、重试和预算可观察；追加历史和 lineage 可查询；全部 Region 有真实 coverage 状态；Christchurch 及其他分散区域有代表性真实验收；证据生命周期可核验；失败不生成 fixture 或伪造结果；后台和 Worker 具备健康、readiness、告警和回滚证据。

### DATA-CORE-022 客户端同版本部署与入口门槛

客户端与后台必须在同一生产版本完成身份、真实 provider 路径、方案权益、Stripe、隐私与安全、浏览器门禁、容量、通知、支持和回滚验收。初期 `DEPLOYED_HIDDEN` 只隐藏首页、公共导航和 CTA；恢复入口只改变展示配置，但必须验证公开关键路径和回滚。
