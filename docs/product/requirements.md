## 状态：Active — National Data Core Product Baseline v1.3｜基线集合：Tymra National Data Core Baseline v1.3｜基线日期：2026-08-21

文档定位：本文件定义 Tymra 当前开发版本的产品目标、目标用户、业务价值、全国数据核心、自动化运营模式、完整生产部署范围、成功指标、合规边界和业务验收标准。详细判断见《业务规则》，页面和用户流程见《页面结构》，视觉和组件实现见《视觉交互》。第十七章同时定义 Codex 一次性开发的固定技术默认值、交付物和完成标准。

## 基线控制

当前生效范围是一个完整生产部署：新西兰全国住宿市场数据核心、单人可运营采集后台、公开 Price Check、客户登录、Free／Host／Pro／Portfolio 会员体系、会员价格、Stripe Billing、客户结果与监测能力一起构建、部署和验收。Christchurch 仅作为早期真实验收市场，不再是产品或采集范围边界。初期只隐藏公开 Price Check、登录、会员、Pricing 和客户结果的首页／导航／CTA 入口，状态记为 `DEPLOYED_HIDDEN`；对应路由、API、Worker、数据库、Stripe 和安全控制仍属于同一生产版本，不得因入口隐藏而跳过实现或验收。
Active 表示本文件已经成为产品、设计、开发和验收的正式依据，不表示全部功能已经开发完成或公开上线。  
文档职责与优先级：《需求说明》负责产品目标、范围、承诺和业务验收；《data-core.md》负责当前全国采集后台的数据对象、覆盖、时间、质量、历史和来源链路；《业务规则》负责通用领域状态、阈值和默认值；《页面结构》负责路由、页面内容顺序和用户流程；《视觉交互》负责视觉令牌、组件状态、布局与动效。发生冲突时依次服从《需求说明》及其指定的领域权威文件；非权威文档只引用对应标识，不重复定义阈值、状态或尺寸。任何新增范围、CTA、页面、业务状态、数据承诺或验收标准，必须先更新对应权威文档并提升基线版本。

## 当前会员体系

以下客户能力属于当前完整生产部署，并在初期以 `DEPLOYED_HIDDEN` 方式运行：入口不出现在首页、公共导航或营销 CTA，但路由和后端能力随同一版本部署并接受生产验收：

- 独立的邮箱用户名与密码登录、退出和客户会话恢复；注册邮箱必须验证后才可启动付费采集；
- Free、Host、Pro、Portfolio 四档方案及其服务器端权益；
- 会员账户首页、定价单位、检查历史、未来价格范围、监测、提醒、账单和方案管理；
- Pro/Portfolio 的组合视图、控制、导出以及 Portfolio 的只读 API/Webhook，但必须分别通过上线门槛后才能显示为可用；
- Stripe 月付订阅、升级、降级、取消、恢复续费、付款失败宽限期和账单门户。
- 单人运营后台中的会员查询、账单事件/对账、会话撤销、暂停、数据请求、审计和隐私安全监控。
- 跨账号 Benefit Group、一次性/滚动权益唯一领取、设备与物理房源双信号关联、支付工具 HMAC 指纹、挑战/冷却、申诉和带原因审计的人工复核；共享 IP 不得单独构成封禁依据。

以下内容不在当前范围：团队成员、邀请、客户角色、多人审批、PMS/Channel Manager 写入和自动调价。

会员商业权益与价格以《membership-plans.md》为权威来源；客户账号密码、Price Check 验证 Magic Link 和会话安全以《customer-funnel.md》为权威来源；会员路由、页面和导航以《page-structure.md》为权威来源；实现及验收状态以《traceability.md》为唯一事实源。隐藏入口只控制发现性，不提供安全边界；所有直接访问仍执行认证、资源归属、方案权益、防滥用和支付状态检查。

## 长期数据平台定位澄清（2026-08-21）

Tymra 当前的长期核心定位是“新西兰住宿市场情报基础设施”，不是无边界收集所有新西兰数据的通用数据中心。系统应持续汇聚、标准化并关联与住宿需求、供给、价格和可售变化有关的合法数据，形成长期连续、可追溯、可比较的数据资产。

会员端是这套数据核心的第一个商业产品出口，与采集后台一起部署但初期隐藏公开入口。其能力包括房源或地址识别、公开价格比较、市场信号解释、逐日价格判断和持续监测。未来可以在同一数据核心上形成酒店集团、旅游市场、住宿投资、活动影响或 API／数据服务等独立产品端，但每个新产品端、客户群和商业承诺都必须单独批准、验证并进入对应基线。

# \[PRD-PRODUCT\] \[PRD-OVERVIEW\] 一、产品概述

## 1.1 产品定位

Tymra by Synix 是面向新西兰住宿经营者的住宿价格情报产品，帮助小型酒店、Motel、Serviced Apartment、独立短租运营者和小型住宿管理公司，识别可能定价过低的高价值日期，理解相关竞品、市场价格和可售变化，并确定需要优先检查的事项。  
Tymra 的核心不是向用户展示更多原始市场数据，而是把可靠的市场观察转化为可解释、可追溯、可执行的日期级价格情报。
产品页面和会员功能是数据能力的交付界面，不是长期壁垒本身；长期壁垒来自持续运行的新西兰住宿市场采集机制、稳定实体身份、不可变历史、质量信息和可复核的数据来源链路。

## 1.2 当前版本定义

National Data Core v1.3 是 Tymra 首次生产部署的统一版本。它同时包含全国数据核心、内部运营后台和完整客户会员产品；客户端初期不出现在首页、公共导航和营销 CTA，但不是另行开发、另行部署或关闭交付。系统持续完成全国身份发现、计划与按需采集、标准化、历史追加、覆盖计算、质量判断和异常处理。只有身份不确定、数据冲突、来源故障、异常变化或其他明确例外才进入人工复核。
当前版本不以“每条数据都由人工审核”为正常流程，也不允许通过人工搬运数据维持日常运行。人工主要处理系统明确标出的异常、来源运行和规则改进；通过直接路由进入的合法客户请求必须能够完成 Price Check、会员登录、购买、结果查看和监测流程。

## 1.3 核心价值

英文核心表达：Find the dates you may be selling too cheaply.  
中文核心表达：快速发现你的房源哪些日期可能卖便宜了。  
产品必须回答：  
• 我现在是否可能卖便宜了？  
• 哪些日期最值得优先检查？  
• 市场发生了什么，为什么需要关注？  
• 我可以采取什么动作，结果的可信程度如何？  
营销问题可以使用“How much revenue are you leaving?”吸引注意，但在缺少真实库存、入住率和预订数据时，不得展示具体损失收入，也不得暗示该金额已被准确计算。

## 1.4 产品边界

Tymra 不是完整的 Revenue Management System，当前版本不自动修改 OTA 或 PMS 价格，不替用户作出最终定价决定，也不保证收入增长或建议必然获得预订。

# \[PRD-USERS\] 二、目标用户与业务问题

## 2.1 第一优先用户

当前产品重点服务管理 1–20 个可独立定价住宿单位、没有专职 Revenue Manager、主要依赖人工查价的经营者，包括小型酒店、Motel、Serviced Apartment、独立短租经营者和小型住宿管理公司。
大型连锁酒店、复杂集团库存、企业协议价、团体价、长期合同价和需要完整收益管理系统的客户不属于当前首要范围。

## 2.2 主要问题

• 无法快速判断自己的价格是否低于真正可比较的住宿。  
• 手动查看多个 OTA 耗时、零散且难以持续保存历史。  
• 容易错过假期、活动、季节变化、竞品集体涨价和可售收紧。  
• 附近房源不一定是真正竞品，错误的竞品会导致错误结论。  
• 现有工具往往展示大量数据，却没有明确告诉用户先处理哪些日期。  
• 小型经营者不愿连接复杂系统，也不愿把价格控制权直接交给自动调价工具。

## 2.3 核心使用场景

• 输入受支持 OTA Listing URL，获得目标 Listing 的未来公开价格检查；或输入真实新西兰地址，获得周边公开住宿行情基准。
• 查看最多 5 个最值得关注的日期及其原因。  
• 了解目标房源相对相关竞品的价格位置和市场变化。  
• 对竞品、洞察和建议提供低成本反馈。  
• 在需要持续监控前，先通过一次真实检查验证产品价值。

# \[PRD-GOALS\] \[PRD-PRINCIPLES\] 三、当前目标与产品原则

## 3.1 正式上线目标

当前目标是建立一个可以由一名运营者维护、主要依靠系统自动完成、能够长期运行全国采集并积累可追溯市场历史的生产级闭环，而不是先上线营销页面或依赖人工逐条维护数据。

## 3.2 自动化优先

• 正常且高质量的请求应自动完成和自动交付。  
• 自动化覆盖输入校验、房源候选识别、数据采集、标准化、竞品候选、去重、分析、结果生成、链接和邮件通知。  
• 系统必须能够根据质量门槛决定自动发布、进入异常复核或返回数据不足。  
• 增加人工步骤不能作为长期替代自动化能力的默认方案。

## 3.3 异常驱动人工介入

• 人工复核不是每个 Price Check 的固定步骤。  
• 只有房源或房型匹配不确定、费用缺失、数据冲突、异常价格、竞品相关性不足、来源故障、用户举报或高风险结论未通过二次验证时才进入人工队列。  
• 人工只处理争议点，不重新执行系统已经完成的全部工作。  
• 数据不足或不支持的请求优先自动返回明确状态，不应全部转化为人工调查任务。

## 3.4 单人可运营

• 当前运营模型以一名产品与运营负责人可以独立管理为约束。  
• 后台默认展示需要决定的异常，而不是要求运营者浏览所有正常任务。  
• 系统应自动准备建议、差异、证据和结果预览，使单个异常能够在少量操作内完成。  
• 数据采集、计算、报告生成、链接创建、邮件发送、审计记录和状态更新不得依赖人工复制粘贴。

## 3.5 市场数据库优先

每次真实检查和市场覆盖采集都必须同时建设 Tymra 自有市场数据库。数据不应只存在于一次性结果或临时缓存中；可合法保存的市场观察、房源身份、房型、Listing、竞品关系、市场信号、数据质量和用户反馈必须形成可追溯的数据资产。

## 3.6 真实性和质量

• 结果质量优先于覆盖范围和结果数量。  
• 只展示实际具备的数据和能力，不使用虚假统计或过度承诺。  
• 数据不足时可以不给出价格建议，不能为了每次都有结果而强行输出。  
• 结果必须说明发生了什么、为什么重要、建议做什么、数据时间和置信度。  
• 用户始终保留最终定价决定权。

# \[PRD-SCOPE\] 四、当前正式范围

## 4.1 端到端用户流程

全国计划或内部按需任务 → 确认数据域、地域、来源 capability 和查询条件 → 创建持久 Collection Run → 自动采集、标准化和质量判断 → 追加身份、观察与变化历史 → 必要时进入异常处理 → 更新全国覆盖、Freshness、Confidence 和 lineage → 内部后台查询与复核。

客户流程：通过直接路由或未来恢复的公开入口 → 选择 OTA Listing 定价或地址周边行情 → 验证／登录 → 应用会员额度与入住条件 → 自动采集和分析 → 返回所有有效价格 → 独立判断推荐 → 保存结果、监测和账单状态。该流程与后台共享身份、来源、观察和 lineage，不建立第二套数据架构。

两种流程都可以异步完成。系统不得为了表现速度而伪造进度；任务必须保留稳定 Job／Run ID、真实状态、失败分类、重试和审计。客户端入口隐藏时，直接创建的合法客户任务仍按完整流程执行。

## 4.2 当前必须交付

• 新西兰全国 Property、Listing、Sellable Unit 和标准地址身份目录。
• 全国公共市场信号与分层代表性 OTA 价格／可售面板。
• 内部运营者可对新西兰地址或受支持 Listing URL 发起有界按需采集。
• 公开价格、可售、限制、费用口径、入住条件和 Collection Profile 标准化。
• 候选竞品自动生成、跨平台去重、相关性判断和关系保存。  
• 全国覆盖等级、Freshness、Confidence、质量限制和异常状态。
• 单人使用的 Exception Inbox、来源健康、Collection Run、市场覆盖和数据资产查询。
• 从第一天运行的追加市场历史、版本化身份、Listing 变化和 Data Lineage。
• Argus Job 证据核验、正确 ACK／purge 和 Tymra 长期标准化事实边界。
• 行为事件、业务指标、错误日志、告警和审计记录。  
• 健康、readiness、暂停、恢复、重试、熔断、容量边界和回滚能力。
• 与后台同版本部署的公开 Price Check、客户邮箱密码登录、四档会员、方案价格、Stripe Billing、客户结果、逐日范围、监测、提醒、历史和账单门户。
• 客户端入口可通过服务端展示配置从首页、导航和公开 CTA 隐藏；隐藏状态下直接路由仍执行完整认证、权益和资源归属检查。

## 4.3 当前明确不交付

• 自动修改 OTA、PMS 或 Channel Manager 中的价格。  
• 完整 Revenue Management System 或完整收益预测。  
• 复杂企业账户、团队权限和审批链。  
• 海外市场的真实分析。
• 未经授权的私有库存、预订或客户数据。  
• 无法合法使用、长期保存或生成衍生分析的第三方数据。

## 4.4 CTA 与承诺边界

初期首页、公共导航和公开 CTA 不展示 Run Free Price Check、会员登录、Membership／Pricing 或订阅入口，但这些能力仍随同一生产版本部署。恢复入口只改变产品发现性，不绕过生产门槛。内部后台必须按区域和数据域显示 Supported、Partial Coverage、Pilot、Insufficient Data 或 Source Unavailable。
不得使用 guaranteed revenue increase、AI knows the perfect price、automatic pricing、complete live market coverage 等超出当前能力的承诺。“Live”只能在数据和更新频率真正满足相应含义时使用，其他情况使用 recently checked 并显示采集时间。

# \[PRD-AUTOMATION\] 五、自动处理与人工介入模式

## 5.1 自动完成路径

满足业务规则规定的房源唯一匹配、Sellable Unit 明确、数据完整、竞品数量达标、费用可标准化、无严重冲突且结论通过质量门槛时，系统应自动生成、发布和交付结果，不进入人工队列。

## 5.2 异常复核路径

系统应只把具体异常发送到 Exception Inbox，并同时提供建议决定、相关证据和可能影响。运营者可以接受建议、修改一个值、排除竞品、重新采集、降低置信度、标记数据不足或批准发布。

## 5.3 自动返回路径

无法获得可靠目标价格、有效竞品不足、房型无法确认、来源不可用、市场未开放或条件不可比较时，系统应自动返回 Needs confirmation、Unsupported、Coming soon、Source unavailable 或 Insufficient data；“Retry later”仅作为 Source unavailable 的用户文案。该路径是正常产品结果，不等于系统失败。

## 5.4 人工效率目标

稳定运行后的目标是：支持范围内至少 80% 的可交付 Price Check 无需人工处理；进入人工队列的比例不高于 20%；单个异常的人工处理中位时间不高于 5 分钟。上线初期可以进行抽样质量检查，但不得把每单全量审核固化为长期流程。

## 5.5 高风险结论

High priority 等高影响结论必须先执行自动二次验证。只有二次采集或独立证据仍存在冲突时才要求人工确认；人工确认应记录依据和版本，但当前不设置必须由第二名人员审批的虚假流程。

# \[PRD-DATA\] 六、Tymra 市场数据库

## 6.1 战略要求

市场数据库是当前核心产品能力和长期壁垒，不是后续数据仓库项目。系统必须从第一次采集开始保存合法、可追溯且不可被新值直接覆盖的市场历史。

## 6.2 核心数据域

• Property：物理住宿地点或经营实体。  
• Sellable Unit／Room Type：可独立出售和定价的住宿单位。  
• Listing：Sellable Unit 在具体平台或渠道上的页面及映射。  
• Rate Observation：特定查询条件和采集时间下观察到的价格、费用、限制和可售状态。  
• Competitor Relationship：目标单位与竞品单位之间的 Core、Reference 或 Excluded 关系及历史。  
• Market Signal：节假日、学校假期、重要活动、价格上涨和可售收紧等信号。  
• Price Check、Insight、Result Version：每次检查、洞察、结果和分析版本。  
• User Feedback、Action Record：竞品相关性、结果评价和用户后续动作。  
• Data Source、Collection Run、Quality Issue：来源、采集批次、运行状态、失败和质量问题。

## 6.3 历史快照原则

Rate Observation 和已发布结果采用追加和版本化模式。新的价格、可售状态或分析版本不得覆盖旧记录。每份结果必须能够追溯到当时的数据快照、采集时间、竞品集合、分析规则、系统版本和人工修改。

## 6.4 两种采集模式

On-demand collection：用户提交检查时，刷新目标房源、候选竞品和本次查询日期所需数据。  
Market coverage collection：系统针对正式支持市场、已知 Property、Sellable Unit、核心竞品关系、重点周末、假期和活动日期执行计划采集，持续积累历史并提高后续检查速度。

## 6.5 当前全国范围

新西兰全国是当前正式采集范围。系统必须覆盖全部 Region，并逐步覆盖 Territorial Authority、主要城市、旅游目的地和小型区域市场；不得以 Christchurch 数据代表全国。Christchurch 只保留为首个真实验收和回归样本市场。

“全国覆盖”不等于抓取所有房源未来 365 天的全部 OTA 组合。当前全国覆盖由五层组成：全国 Property／Unit／Listing 身份目录、全国公共市场信号、分层代表性 OTA 价格与可售面板、任意已解析新西兰地址或受支持 OTA URL 的按需采集，以及会员已激活房源的方案化逐日监测。五层都属于当前统一生产版本；初期入口隐藏不改变第五层的部署、权益校验或运行验收要求。

所有可解析的新西兰区域都可进入采集和查询流程，但输出必须携带 `coverageTier`、样本覆盖、Freshness、Confidence 和限制。区域质量按 `SUPPORTED`、`PARTIAL_COVERAGE`、`PILOT`、`INSUFFICIENT_DATA` 或 `SOURCE_UNAVAILABLE` 透明降级，不得因全国范围目标而伪装同等质量。

## 6.6 数据复用与学习

已确认的 Property、Sellable Unit、Listing 映射和竞品关系应优先在后续检查中复用，同时根据新数据、人工修正和用户反馈更新版本。人工调整必须进入可审计的数据闭环，避免同类问题反复由人工处理。

## 6.7 数据来源和运行状态

每条可用于分析的市场数据必须记录来源、采集时间和质量状态。只有已启用且运行健康的来源数据可以进入正式自动发布路径。

## 6.8 核心数据资产管理

市场数据库必须统一实现以下能力，而不是由每个页面或 Connector 各自维护一份事实：

• Source Registry：记录来源身份、负责数据域、可调用能力、获取方式、生命周期、启用状态、健康状态、采集频率、并发与成本边界、负责人、保留策略和最近成功时间。
• 时间语义：至少区分来源发布时间或生效时间、实际采集时间、业务适用日期和 Tymra 入库时间；缺少必要时间语义的数据不得被描述为实时或新鲜。
• 数据分层：短期原始证据、标准化事实和分析衍生结果必须分层管理，分别执行隐私、保留和清理策略。
• Confidence 与 Freshness：每条用于结果的数据必须携带可解释的质量与新鲜度状态；数据是否存在、是否可信以及是否足够新是三个不同判断。
• 地址与 OTA 身份映射：真实地址、Property、Sellable Unit 和各 OTA Listing 必须形成版本化身份图谱，保存匹配依据、置信度、首次发现、最后确认、冲突、合并和拆分历史。
• Listing 变化历史：新增、下线、重新上线、名称、品牌、房型、政策、公开价格和可售状态变化不得只保留最新值。
• Data Lineage：每个价格、市场信号、快照、洞察和建议都必须能够追溯到标准化记录、采集批次、来源、时间、规则／模型版本及允许保留的证据或内容哈希。

Data Lineage 不要求永久保存 OTA HTML、截图、Cookie、Session 或其他短期原始材料。Argus 证据可以按 ACK 和保留策略清理；Tymra 应长期保留合法的标准化事实、来源标识、采集时间、质量状态、结果哈希和转换链路。

上述要求的字段、覆盖层、质量语义和验收标识以《data-core.md》的 `DATA-CORE-*` 条款为准。

# \[PRD-RESULT\] 七、分析范围与用户结果

## 7.1 正式分析单位

正式分析单位为 Sellable Unit，即可独立出售和独立定价的房型或住宿单位。Property、Listing、Sellable Unit 和 Room Type 必须分开建模。多房型酒店或 Motel 必须确认具体房型，不能直接生成整家酒店的统一价格判断。

## 7.2 默认检查范围

免费真实检查默认覆盖一个 Sellable Unit、未来 30 天、最多 5 个重点日期。具体入住人数、单位数、住宿晚数、时区和可比条件由《业务规则》定义，用户应能确认必要条件。

## 7.3 结果最低内容

• Property 和 Sellable Unit。  
• 查询日期范围、人数、单位数和住宿晚数。  
• Generated at、Data last checked 和 Analysis version。  
• 整体 Confidence。  
• 最多 5 个重点日期。  
• 目标价格和聚合竞品中位价或区间，前提是来源可用且数据通过质量门槛。
• 风险等级、主要原因和市场信号。  
• 建议动作和明确限制。  
• 用户反馈和问题举报入口。

## 7.4 结果类型

系统必须支持 Normal result、Partial result、Insufficient data、Needs confirmation、Unsupported、Source unavailable、Failed、Expired 和 Withdrawn。无法形成可靠结论时，不得生成虚假价格、竞品或调价建议。

## 7.5 安全交付

正式结果通过已认证客户会话交付，服务邮件只提供站内结果入口，不携带持久 bearer 访问权限。一次性 `VERIFY_AND_SIGN_IN` token 只用于验证并建立会话，消费后从 URL 移除。每次结果读取都执行客户归属、会话、会员状态和资源授权检查。

# \[PRD-OPS\] 八、运营工作台要求

## 8.1 Exception Inbox

后台首页以 Exception Inbox 为核心，只优先显示需要人工决定的任务，包括匹配不确定、竞品异常、数据冲突、来源失败、高风险复核和用户举报。正常自动完成和正常数据不足任务不得占据主工作队列。

## 8.2 单屏决策

每个异常应在同一工作区展示：原始输入、系统建议、冲突字段、关键证据、可能影响、结果预览和允许动作。运营者不应在多个页面、Excel 和浏览器窗口之间重复搬运数据。

## 8.3 必备效率能力

• 一键接受系统建议。  
• 只高亮冲突字段。  
• 竞品快速确认、排除和批量操作。  
• 重新采集和重新分析。  
• 自动保存、自动审计和下一任务切换。  
• 相同异常的批量处理和规则反馈。  
• 自动生成结果、链接和通知。

## 8.4 市场运行视图

后台还应提供 Market Coverage、Data Source Health、Collection Runs、失败重试、Property 与 Sellable Unit 查询、竞品关系查询、结果版本和审计日志，但这些视图不应阻碍日常异常处理。

# \[PRD-MARKET\] 九、地域、语言与住宿范围

## 9.1 地域

真实价格检查首期仅支持新西兰房源。用户可以从其他国家访问网站，但非新西兰房源不得进入真实分析，也不得使用新西兰市场生成替代结果。

## 9.2 住宿范围

首期支持能够明确识别 Sellable Unit 的小型酒店、Motel、Serviced Apartment、独立短租和小型住宿管理公司。复杂集团库存、企业协议价、团体价和长期合同价不属于当前范围。

## 9.3 双语

当前版本必须提供完整英文和简体中文体验，覆盖公开网站、输入与确认、任务状态、结果、系统邮件、错误、法律文件和免责声明。语言切换只改变表达，不改变数据、竞品集合、风险等级、置信度或建议动作。
英文为默认语言。中文版面向在新西兰经营住宿业务的中文用户，不代表支持中国境内房源。房源名称、地址、OTA 名称和专有名词保留官方形式。

# \[PRD-COMMERCIAL\] 十、客户端与商业化边界

## 10.1 当前部署与展示状态

免费检查、会员登录、方案价格、订阅和客户结果与后台一起部署并完成生产验收，初期仅隐藏首页、公共导航和营销 CTA 入口。后台采集数据持续全国积累；隐藏配置不应停止会员相关 Worker、账单 webhook 或数据生命周期能力所需的健康检查。

## 10.2 当前不包含的付费能力

团队协作、PMS／Channel Manager 集成和自动调价不属于当前范围。客户价格日历、持续监控、提醒、多房源组合、客户历史和会员订阅账单属于当前部署范围，具体权益由《membership-plans.md》控制。

## 10.3 付费验证

首次生产部署前必须完成真实 provider、套餐、计费、取消、通知、容量、支持和回滚验收。入口隐藏期间仍必须部署并验证客户页面、身份、Stripe webhook、权益、结果和数据生命周期，不能用隐藏状态代替完成定义。以后恢复公开入口时只需重新验证展示配置、公开关键路径和回滚，不重新引入一套客户架构。

# \[PRD-ROLES\] 十一、用户角色

• Tymra 单人运营者：处理 Exception Inbox、维护市场覆盖、处理来源故障、复核用户举报和管理产品配置。  
• 系统自动化服务：执行全国采集、标准化、匹配、质量门槛、历史保存、lineage 和运行监控。
• 系统管理员：当前可与单人运营者为同一人员，但权限、审计和生产配置仍应按最小权限设计。
• 访客／住宿经营者：使用随生产版本部署但初期隐藏入口的 Price Check、会员和客户结果能力。

# \[PRD-METRICS\] 十二、当前数据核心退出标准

## 12.1 全国覆盖

• 全部新西兰 Region 均有明确 coverage 状态，不以 Christchurch 代替全国。
• 全国身份目录、公共市场信号和代表性 OTA 面板分别报告覆盖率、Freshness、成功率和缺口。
• 至少使用 Christchurch 以及分散在其他 Region 的代表性样本完成真实采集验收。
• 当前来源统计直接来自实际 Source Registry 配置，不混入未启用或不在当前范围的来源。

## 12.2 自动化与单人运营

• 可执行采集任务的自动完成率达到或超过 80%。
• 人工介入率不高于 20%。  
• 单个异常的人工处理中位时间不高于 5 分钟。  
• 已接受 Collection Run 的明确终态率不低于 90%。
• 运营者无需依靠 Excel、聊天记录或人工复制粘贴维持正常流程。

## 12.3 质量

• 抽样范围内 Property、Sellable Unit 和 Listing 身份匹配准确率达到批准门槛。
• 使用的数据必须满足对应数据域的 Freshness、身份、字段完整性和冲突门槛。
• 来源失败、字段冲突和人工修改能够定位到 Source、Collection Run、转换版本和历史事实。
• 一个有效公开价格必须保存并返回；竞品或信号不足只限制推荐，不隐藏该价格。

## 12.4 市场数据库

• 100% 用于正式衍生结果的事实可追溯到 Source、Collection Run／Argus Job、查询、采集时间、转换版本和证据引用／哈希。
• Rate Observation、Listing 变化、身份关系和结果版本不被新值覆盖。
• 所有人工竞品修正和匹配修正进入版本化、可复用的数据关系。
• 全部 Region 具有可监控的覆盖范围、Freshness、失败率、来源健康和覆盖缺口。

# \[PRD-NFR\] 十三、生产上线与非功能要求

National Data Core v1.3 是 Tymra 首次统一生产部署版本，后台与客户会员能力共同满足以下要求：
• 开发、测试和生产环境隔离。  
• 数据库迁移、备份、恢复和回滚方案。  
• 异步任务、重试、幂等和超时处理。  
• 数据采集、标准化、lineage、覆盖和异常的日志与告警。
• 来源故障和市场覆盖降级能力。  
• 隐私、同意、数据删除和保留机制。  
• 最小权限、密钥管理和审计记录。  
• 内部后台关键桌面流程，以及客户端中英文桌面／移动关键流程可用并满足基础无障碍要求。
• 生产故障时可以暂停调度、单一来源或按需采集，而不破坏历史数据。
• 客户和会员路由随生产版本部署，初期不可由首页、公共导航或营销 CTA 到达；直接访问仍执行完整安全控制。

# \[PRD-COMPLIANCE\] 十四、合规、责任与商业秘密

## 14.1 隐私与营销

必须明确收集的数据、目的、保存期限、产品改进用途、删除方式、第三方共享和未来 PMS 数据范围。服务通知与营销必须分开，营销邮件需要单独同意。

## 14.2 数据运行控制

每个第三方来源必须具有明确的启用开关、健康检查、请求预算、保留期限和停用路径。

## 14.3 产品责任

Tymra 提供价格情报和决策支持，不保证收入增长或建议必然获得预订。结果必须显示数据时间、置信度和限制，用户负责最终定价决定。

## 14.4 商业秘密

用户应获得可解释结论，但不得公开完整评分公式、精确权重与阈值、内部特征、相似度分数、来源组合和模型差异。算法细节保存于受限决策文档；长期壁垒应来自合法历史数据、竞品关系、市场知识、用户反馈和工作流。

# \[PRD-AT\] 十五、业务验收标准

PRD-AT-001 全部新西兰 Region 在内部后台具有真实覆盖状态，并可下钻查看来源、Freshness、成功率和缺口。
PRD-AT-002 全国计划任务和内部按需地址／Listing 任务可在支持范围内无需人工介入完成。
PRD-AT-003 明确异常进入 Exception Inbox，且运营者只需处理争议点。  
PRD-AT-004 数据不足、不支持和来源故障不会生成虚假结果。  
PRD-AT-005 每次有效采集都进入市场数据库，并保留来源、查询条件、时间和质量状态。  
PRD-AT-006 每个正式衍生结果能够完整追溯至 Collection Run／Argus Job、标准化事实、转换版本和证据引用／哈希。
PRD-AT-007 确认过的 Property、Sellable Unit、Listing 和竞品关系能够在后续任务中复用。  
PRD-AT-008 短期证据按 Argus ACK／purge 合同清理，长期标准化历史和 lineage 不被连带删除。
PRD-AT-009 生产环境具备日志、告警、备份、恢复以及暂停调度、按需采集或单一来源的能力。
PRD-AT-010 同一生产部署包含客户登录、会员、Pricing、Stripe Billing 和客户结果；隐藏配置启用时首页、公共导航和营销 CTA 不暴露入口，直接访问仍通过完整认证与权益校验。

# \[PRD-ROADMAP\] 十六、阶段路线图

## 16.1 当前开发版本

同一生产版本包含：新西兰全国身份目录、公共市场信号、代表性 OTA 面板、内部按需采集、追加历史、质量与 lineage、异常驱动人工介入、单人可运营后台，以及完整 Price Check、客户登录、Free／Host／Pro／Portfolio、Stripe Billing、客户结果和监测。Christchurch 仅作为早期验收市场。客户端入口初期隐藏但能力一同部署。

# \[PRD-CODEX\] 十七、Codex 一次性开发执行契约

## 17.1 执行目标

《需求说明》《data-core.md》《业务规则》及其引用的技术与追踪文档共同构成 Tymra National Data Core Baseline v1.3。所谓“一次性开发”是指 Codex 在一个连续任务中完成仓库审计、实现、数据库变更、测试、修复和文档交付，不是跳过验证，也不是用模拟结果冒充生产能力。Codex 可以在内部按阶段工作，但最终必须交付一个可本地运行、可测试、可统一部署的全国数据后台与完整客户会员产品。

会员能力与后台属于同一开发和部署基线，不得因入口隐藏而跳过 `MEM-*` 的独立认证、账户、Billing、Worker 和浏览器验收。

## 17.2 解释优先级与默认决策

文档冲突时先服从《需求说明》，全国数据核心领域服从《data-core.md》，通用业务状态服从《业务规则》，客户路由和交互分别服从《页面结构》《视觉交互》和《customer-funnel.md》。Codex 不得自行扩大范围；遇到文档未明确但不影响业务承诺的实现细节时，应采用本章默认值并记录在仓库 docs/decisions.md。

## 17.3 默认技术基线

若目标仓库已有技术栈，Codex 应按当前基线直接维护；若为空仓库，默认使用 pnpm workspace：apps/web 为 Next.js App Router、React、TypeScript；apps/worker 为 Node.js TypeScript 后台任务；packages/domain、db、providers、config 分别保存领域逻辑、数据库、数据提供者和共享配置，Web 组件按消费者保存在 `apps/web/components`。界面使用现有 Tailwind CSS、lucide-react 和 Motion 能力。数据使用 PostgreSQL 与 Prisma，校验使用 Zod，后台任务使用 PostgreSQL 支持的持久任务队列。运营后台与客户账户使用相互隔离的安全会话；客户路由随生产版本部署，展示配置只隐藏入口，不关闭认证、API 或 Worker 能力。邮件、分析和错误监控均通过适配器接入。

## 17.4 数据提供者与真实数据约束

系统必须实现 capability-based Data Provider Registry、可在生产使用的 Manual Import Provider，以及仅限开发和测试的 Demo Provider。来源只注册自身真实支持的能力；任何 OTA、公共页面、API 或导入适配器只有在任务所需 capability 存在、配置完整、已启用且运行健康后才能执行。生产环境严禁使用 Demo Provider、固定假数据或随机数据生成真实结果。没有可用来源时，后台、数据库和任务系统仍须可运行，但相关任务必须返回 SOURCE\_UNAVAILABLE，不得伪造市场结果。

## 17.5 必须交付的仓库内容

Codex 必须交付：Exception Inbox；全国 Market Coverage、来源健康、Collection Run、身份、历史、lineage、审计和异常视图；完整公开 Price Check、客户账户、会员方案、Pricing、Stripe Billing、客户结果和监测；数据库模型、迁移和开发种子；后台任务、调度、重试、熔断和证据生命周期；环境变量示例；Dockerfile 与 docker-compose；持续集成配置；README、架构说明、来源接入说明、上线运行手册和 docs/traceability.md。生产导航与 CTA 默认隐藏客户入口，但相应路由、API、Worker 和 webhook 必须随同一版本部署。已启用来源必须具有真实 capability、健康检查和配置入口。

## 17.6 测试和完成定义

交付前必须通过 lint、类型检查、单元测试、领域规则测试、数据库集成测试、任务幂等／租约／重试测试、后台和客户端关键浏览器流程以及生产构建。至少覆盖全国 coverage、来源 capability、追加历史、时间、Freshness、Confidence、lineage、地址／Listing 两种模式、单价格返回、证据 ACK／purge、异常复核和来源故障。本地必须能够通过 docker compose up \--build 启动；迁移和开发种子必须可重复执行。`DEPLOYED_HIDDEN` 必须同时验证公开导航／CTA 不显示入口、直接路由仍部署、认证与权益不被绕过。任何失败测试都必须在同一任务中修复，而不是只写入已知问题。

## 17.7 需求追踪

仓库必须生成 docs/traceability.md，将 PRD、DATA-CORE、BR 以及适用的 PG 和 UI 标识映射到代码模块、数据库对象和测试用例。每项当前后台必交付能力必须至少对应一个自动化测试。代码中的状态枚举、错误码、事件名和文案键必须与权威文档一致，禁止另行创造同义状态。

## 17.8 外部上线门槛

完整开发不等于生产可持续运行。同一部署必须具备真实来源、生产数据库、全国调度配置、来源预算、健康与告警、备份恢复、证据清理、客户身份、真实 provider 绑定、Stripe、发信、隐私安全、浏览器、容量、支持和回滚。入口是否公开是独立展示决定，不改变部署完成标准。

## 17.9 环境变量与配置契约

仓库必须提供 .env.example，并在服务启动时使用共享 Schema 校验环境变量。核心变量至少包括：DATABASE\_URL、APP\_BASE\_URL、SESSION\_SECRET、ADMIN\_EMAIL、ADMIN\_PASSWORD\_HASH、RESULT\_TOKEN\_SECRET、ACCESS\_KEY\_SECRET、DATA\_ENCRYPTION\_KEY、CRON\_SECRET、PROVIDER\_MODE、DEFAULT\_MARKET、AUTO\_PUBLISH\_ENABLED、EMAIL\_PROVIDER 和 EMAIL\_FROM。EMAIL\_PROVIDER=smtp 时必须提供 SMTP\_URL；本地开发可使用 EMAIL\_PROVIDER=log。可选变量包括 SENTRY\_DSN 和 ANALYTICS\_ENDPOINT。任何密钥不得提交仓库。生产环境 PROVIDER\_MODE=demo 必须启动失败；PROVIDER\_MODE=manual 只允许使用已在后台启用且运行健康的导入来源，并且不满足自动发布质量门槛时必须返回明确限制状态。

## 17.10 固定开发、测试与 CI 命令

根目录 package.json 必须提供并记录以下命令：pnpm dev、pnpm worker、pnpm db:generate、pnpm db:migrate、pnpm db:seed、pnpm lint、pnpm typecheck、pnpm test、pnpm test:integration、pnpm test:e2e、pnpm build 和 pnpm verify。pnpm verify 必须依次完成 lint、类型检查、单元与集成测试及生产构建。README 必须提供从空数据库开始的可复制启动步骤；docker compose up \--build 必须启动 PostgreSQL、Web 和 Worker。CI 使用 frozen lockfile 安装依赖，运行数据库迁移、pnpm verify 和 Playwright 主流程测试。

## 17.11 生产启动保护

生产启动检查必须阻止以下配置：Demo Provider；默认或空管理员凭证；不足强度的 token、session 或加密密钥；未执行数据库迁移；调度启用但没有具备所需 capability、已启用且健康的数据来源；Stripe 或客户能力启用但关键 webhook、身份或安全配置缺失。系统必须支持全局暂停调度、暂停按需采集和暂停单一来源，并把变化写入 Audit Event。入口隐藏配置必须只影响首页、导航和 CTA，不得绕过认证或改变后台任务。来源不可用时任务 fail closed，不能生成 Demo 结果。
